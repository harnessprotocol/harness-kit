Harness Kit has a portable protocol and reconciliation engine at its center. The CLI and desktop app capture native peer state, preview conflicts and losses, and apply transactional changes. An optional organization registry distributes immutable artifacts and policy and receives redacted inventory; it never executes commands on developer machines. Plugins — SKILL.md files, agents, hooks, and scripts — still run inside the developer's AI tools.

## harness.yaml

`harness.yaml` is the readable, portable reconciliation record for your AI coding setup. Native tool files remain bidirectional peers rather than generated files that Harness Kit silently owns. It follows the [Harness Protocol](https://harnessprotocol.ai) — an open, vendor-neutral specification.

```yaml
$schema: https://harnessprotocol.io/schema/v2/harness.schema.json
version: "2"
kind: profile
scope: project

plugins:
  - name: research
    source: harnessprotocol/harness-kit

mcp-servers:
  memory:
    transport: stdio
    command: mem
    args: [mcp]

instructions:
  operational: "Always create a feature branch. Never commit to main."
  behavioral: "Direct, concise. Lead with the answer."

permissions:
  tools:
    allow: ["Bash", "Edit", "Read"]
    deny: ["WebFetch"]
  network:
    allow: ["api.anthropic.com"]

env:
  - name: ANTHROPIC_API_KEY
    description: Credential resolved locally when a target requires it.
    required: true
    sensitive: true

extends:
  - source: profiles/backend-engineer.yaml
```

The full schema also supports top-level skills, architecture constraints, policy, inheritance, and namespaced target-native vendor blocks. Four ordered layers—organization, personal, project, and session—resolve through the same three-way reconciliation engine. [Harness Protocol spec →](https://harnessprotocol.ai)

## Desktop App

The desktop app is a management console organized into named sections. It reads your harness configuration, provides observability into what your AI tools are doing, and gives you direct control over the pieces that are hard to manage from a terminal.

**CORE**

- **Harness** — view and edit your harness.yaml, CLAUDE.md, plugins, MCP servers, and hooks in a structured UI
- **Marketplace** — browse and install plugins from the registry

**INSIGHTS**

- **Observatory** — session telemetry: every session, every tool call, token usage, timeline, trends

**SYSTEM**

- **Security** — permissions, secrets management, audit log

**Standalone sections**

- **Agents** — detection panel for AI coding agents installed on your machine
- **Comparator** — run the same prompt across Claude Code, Cursor, and Copilot side by side
- **Harness Parity** — after compiling, confirm the same plugins, MCP servers, and skills landed in each connected AI tool, and catch drift
- **Command Palette** — Cmd+K to navigate and operate the app

Memory (a persistent knowledge graph your agents can orient themselves in) is delivered as the `membrain` plugin over MCP, not a standalone desktop app section — see [Memory](/docs/concepts/memory).

## CLI

The `harness` CLI is a standalone terminal tool. You run it from your shell; it is not a plugin and does not run inside an AI tool's session.

```bash
harness validate          # check harness.yaml against the schema
harness compile           # compile harness.yaml into native per-tool configs
harness compile --watch   # recompile automatically whenever harness.yaml changes
harness install           # fetch plugins into local cache, write harness.lock
harness sync              # copy resources between surfaces to close machine gaps
harness check             # detect drift between compiled output and harness.yaml
harness detect            # show which AI platforms are present in the working directory
harness scan              # security audit of installed plugin skill files
harness import            # scan existing AI tool configs and synthesize a harness.yaml
harness capture           # create a secret-safe Protocol v2 peer snapshot
harness reconcile         # preview a three-way layered reconciliation
harness apply             # preview or transactionally apply resolved changes
harness rollback --list   # list rollback points across user and project scope
harness rollback          # restore a complete previous transaction
harness skills promote    # pin or package a repository-local skill
harness org rollout-sync  # preview or apply this device's pinned organization rollout
harness status            # show the fleet: which harnesses are installed, where, and how drifted
harness diff              # show drift between harness.yaml and deployed tool configs
harness fix               # preview (default) or --apply repairs for detected drift
```

**`compile` output** — `harness compile` writes native configuration files for each detected AI tool: `.claude/settings.json` for Claude Code, `.cursor/rules` for Cursor, and so on. Each AI tool then loads those files at session start. This is how harness.yaml becomes active in your AI tools — it is compiled, not interpreted at runtime.

## Plugin System

### Lifecycle

<Steps>
<Step>
**Source** — you register harness-kit as a plugin source in your AI tool. This points to the collection, not individual plugins.
</Step>
<Step>
**Install** — you install a plugin by name. The plugin directory is downloaded locally.

```
/plugin install research@harness-kit
```
</Step>
<Step>
**Discovery** — at session start, your AI tool scans installed plugins and registers any skills it finds.
</Step>
<Step>
**Invocation** — you run a slash command. The matching `SKILL.md` is loaded into context as the workflow definition.

```
/research https://github.com/anthropics/claude-code
```
</Step>
<Step>
**Execution** — the AI follows the steps in `SKILL.md`, using available tools: file I/O, web fetch, shell commands, MCP servers.
</Step>
</Steps>

### Plugin Anatomy

```
plugins/<name>/
├── .claude-plugin/
│   └── plugin.json       # name, version, description
├── skills/
│   └── <name>/
│       ├── SKILL.md      # the workflow (what the AI reads at invocation)
│       └── README.md     # human docs
├── scripts/              # optional: shell automation
├── hooks/                # optional: Stop, PreTool, PostTool handlers
└── agents/               # optional: isolated specialist subagents
```

| Component | Role | When it runs |
|-----------|------|-------------|
| `plugin.json` | Metadata — name, version, description | At install and update |
| `SKILL.md` | Workflow definition | At slash command invocation |
| `scripts/` | Shell scripts called by skills or hooks | On demand |
| `hooks/` | Lifecycle event handlers | On harness lifecycle events |
| `agents/` | Isolated workers with scoped tools and a fresh context window | When a skill delegates to a named agent |

### SKILL.md vs. a prompt

A `SKILL.md` is a **complete workflow specification**, not a prompt template:

- **Mandatory step ordering** — steps execute in sequence, no skipping
- **Input parsing rules** — how to interpret arguments and flags
- **Tool usage patterns** — which tools to call, when, and how
- **Output structure** — exact format for results
- **Error handling** — explicit recovery steps when things fail
- **Common mistakes table** — known failure modes and fixes

This structure makes skills repeatable across sessions and transferable across users. The same `/research` invocation produces the same workflow regardless of who runs it.

## Portability

`harness capture` discovers native configuration and writes a secret-safe Protocol v2 preview. `harness reconcile` compares the last-applied base, current native peer state, and layered profiles. `harness apply` blocks unresolved conflicts and unsupported operations, then writes owned files transactionally with a complete rollback manifest.

Portable fields move between tools. Unmatched native settings remain in target-namespaced vendor blocks and produce an explicit loss report on other targets.

```bash
harness capture                       # preview native peer capture → harness.yaml
harness capture --yes --force         # explicitly write the capture
harness reconcile harness.yaml        # inspect conflicts and capability losses
harness apply harness.yaml --yes      # transactionally apply an approved plan
```

(Available via the [harness-share](/docs/plugins/productivity/harness-share) plugin.)

## Design Philosophy

Harness Kit is a portability and governance layer, not an agent execution runtime. Local clients own capture, reconciliation, apply, health checks, and rollback. The optional organization service stores immutable artifacts, policy, audit history, rollout assignments, and redacted inventory; it cannot run commands on enrolled devices.

`SKILL.md` remains one portable resource, but the protocol also represents plugins, MCP servers, instructions, permissions, environment declarations, architecture constraints, policy, inheritance, and native-only extensions.

The spec is [open](https://harnessprotocol.ai). The format travels.
